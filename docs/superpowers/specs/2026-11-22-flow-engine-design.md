# フローエンジン（core）設計書

日付: 2026-11-22 / 状態: 承認待ち

## 1. 目的と背景

Claude Code の skill の多くは、手順を文章で書いた手順書になっている（「1.1 作業 A をやり、xxx なら 2 へ」「3 は最大 2 周まで」「全体の注意点は…」）。これには次の問題がある。

- **修正しにくい**: 番号やラベルを変えると、参照している箇所をすべて書き換える必要がある。
- **検証しにくい**: AI に確認させても、「行き先がない」「収束しない」といった問題が出て、直すたびに手間がかかる。
- **コンテキストを食う**: 全文を最初に読み込むため、今のステップに関係のない部分まで消費する。

そこで、手順を**定義ファイル（ステートマシン）**として書き、**決定論的なスクリプト**が「今のステップで必要な情報だけ」を LLM に渡す仕組みを作る。構造の検証は、AI の目視ではなく linter で機械的に行う。

## 2. ゴール / 非ゴール / アンチゴール

### ゴール

1. 定義ファイルと状態ファイルから、現在のステップのプロンプト・注意書き・選べる判定ラベルを出力する CLI。
2. 定義の構造的な不具合を検出する linter（孤児ステート、到達できない終了、ラベルなし、無限ループなど）。
3. 定義の作成・編集・レビュー・デバッグを助ける機能（dry-run、ラベル改名、進行状況の確認）と、それを使う core プラグインの skill。
4. 各ステップで LLM に渡す情報量を、そのステップに必要な分だけに抑える。
5. ラベルの改名は 1 コマンドで完結し、壊れたらその場で検出できる。

### 非ゴール（初版ではやらない。詳細は `docs/BACKLOG.md`）

- ステップ単位のサブエージェント委譲（B-001。初版後に実装済み。§6 の `delegate`）。
- MCP サーバー化（B-002）。ただしロジックはライブラリとして呼べる構造にしておく。
- スクリプトによる機械判定ステップ（B-003。初版には含めないと決定済み）。
- Windows 対応（B-004）。
- 実行時のサブフロー（再帰。B-036）と、`rename` による `exits` の値の書き換え（B-037）。部品の読み込み時の展開（`include`）は実装済み（B-017。§6.1）。
- GitHub 経由のインストールでの実機確認（B-005）。これは設計の前提確認であり、実装前に済ませる必要はないが、初版の完了条件には含める。

### アンチゴール（技術的に動いても失敗とみなすもの）

- LLM に、run-id やコマンドの形を覚え続けさせる設計。
- linter を通ったのに、実行すると行き止まりになる定義。
- 定義の全文を、実行中に LLM のコンテキストへ読ませる設計。

## 3. 制約

- 実装は Python 3.11 以上、**標準ライブラリのみ**。`uv run` で実行できること。
- `flow.py` の先頭に PEP 723 のスクリプトメタデータ（`requires-python = ">=3.11"`、`dependencies = []`）を置き、`uv run` が 3.11 以上を選ぶようにする。
- エンジンは**単一ファイル**（`flow.py`）にする。feature プラグインへ symlink で同梱するため（[`README.md`](../../../README.md) 参照）。
- 同梱するため、エンジンは**プラグイン外のファイルに依存しない**。ユーザーの設定ファイルを書き換えない。
- 状態は、作業ディレクトリ（プロジェクト）側に保存する。プラグインのキャッシュには書かない。
- Windows は対象外（symlink を使う）。

## 4. 検討した方法と、選んだ理由

| 論点 | 選択肢 | 選んだもの | 理由 |
|---|---|---|---|
| 状態の持ち方 | A. 状態なし（LLM が毎回ラベルとカウンタを渡す）/ B. 状態ファイル | **B** | LLM が持ち回る情報を最小にできる。圧縮や中断をまたいで再開でき、履歴でデバッグできる。 |
| 呼び出し形態 | 1. CLI / 2. MCP / 3. 両方 | **1** | 人が lint や dry-run を直接叩けることが価値の半分。ロジックを分離しておき、後から 3 へ拡張できる。 |
| 定義の形式 | YAML / TOML | **TOML** | 標準ライブラリで読める。YAML 1.1 では `yes` / `no` が真偽値になり、判定ラベルが静かに壊れる。 |
| 分岐の判定者 | LLM / スクリプト | **LLM が基本** | 分岐は作業結果の解釈を要する。機械判定は将来足す（B-003）。 |
| 呼び出す主体 | 作業した LLM / 呼び出し側 LLM が委譲 | **作業した LLM** | 作業と判断が同じコンテキストにある。委譲は将来足す（B-001）。 |

## 5. 構成

```
shared/flow/flow.py              エンジン本体（単一ファイル、標準ライブラリのみ）
plugins/core/                    定義の作成・レビューを助ける skill 群
plugins/<feature>/
  scripts/flow.py                → shared/flow/flow.py への相対 symlink
  skills/<skill>/
    SKILL.md                     固定ループの短い指示だけを書く
    flow.toml                    その skill の定義
    prompts/, notes/             長いテキスト（任意）
```

- エンジンは、各 feature に symlink で同梱する。core プラグインに実行時の依存は持たせない。
- core プラグインは、**定義の作成・編集・レビュー・デバッグ**を LLM で助ける skill を提供する。これらは、同じ `flow.py` を使う。

## 6. 定義ファイル（`flow.toml`）

```toml
schema = 1
start  = "s1_1"

[notes]
always = ["xyzは禁止", { file = "notes/global.md" }]   # 毎ステップに出す
[notes.common]                                          # 参照したステップだけに出す
abc = "abcに注意"
def = { file = "notes/def.md" }

[states.s1_1]
prompt = { file = "prompts/s1_1.md" }
notes  = ["abc"]

[[states.s1_1.choices]]
label = "xxx"
when  = "ビルドが成功し、警告が 0 件だった"
goto  = "s2"

[[states.s1_1.choices]]
label = "other"
when  = "上記以外"
goto  = "s1_2"

[states.s1_2]
prompt = "作業Bをやる"
goto   = "s2"                  # 分岐なし

[states.s3]
prompt     = "作業Dをやる"
goto       = "s2"
max_visits = 2                 # 超えたら on_exceed へ
on_exceed  = "s4"

[states.s4]
prompt = "完了を報告する"
end    = true
```

### ルール

- **テキスト値**（`prompt`、`always` の各要素、`common` の各値、`when`）は、文字列、または `{ file = "相対パス" }`。パスは定義ファイルのあるディレクトリからの相対で、`..` や絶対パスで外へ出ることは禁止する。ファイルは、そのステップを出力するときにだけ読む。
- **ステート ID** は `^[A-Za-z_][A-Za-z0-9_]*$`。番号（`1.1`）は ID にしない。TOML ではドットが階層になるため。
- **判定ラベル**（`label`）は `^[A-Za-z0-9_]+$`。コマンドライン引数として安全に渡せるようにするため。
- **遷移の書き方**は、次のいずれか 1 つ。
  - `goto = "<id>"`（分岐なし）
  - `[[states.<id>.choices]]` の並び（`label` / `when` / `goto`）
  - `end = true`（終了）
- **`max_visits`**: そのステートに入れる回数の上限。上限に達した後に入ろうとしたとき、入らずに `on_exceed` のステートへ移る。`max_visits` を書いたら `on_exceed` も必須。
- **`delegate`**: 任意。そのステートの作業を任せるサブエージェントの名前（文字列）。`render_step` が、ステップ全文を委譲先に渡し、委譲先が `next` コマンドまで実行して出力を返すよう案内する。モデルとツールは `agents/` の定義側に持たせる。終了ステートには書けない。
- **`gate`**: 任意（B-016）。`true` のステートは、人の承認を手順として求める。`render_step` が「ユーザーに確認し（`AskUserQuestion` などを使う）、却下されたら進めない」という案内と、`next` の `--approval "<ユーザーの回答>"` を足す。`gate` のステートから進むときは `flow next --approval` が必須（なければエラー）で、回答は時刻とともに `history` の `approval` に残り、`status` にも出る。`gate` でないステートに `--approval` を渡すとエラー。エンジンは回答の真偽を確かめられないので、強制ではなく記録である。終了ステートには書けない。
- **未知のキー**は、すべて lint エラー（typo の検出のため）。

### 6.2 start への引数（B-018）

- 定義の `[args.<名前>]` で引数を宣言する。名前は ID と同じ形式。キーは `required`（真偽、既定 false）と `default`（文字列）。型は文字列のみ。`required = true` と `default` は併記できない（`arg-default-required`）。
- `flow start --arg key=value` で渡す（繰り返せる。値に `=` を含んでよい）。未宣言のキー、必須の引数の欠落、同じキーの重複は、run を作る前にエラーにする。既定値を適用した結果を run の `args` に記録し、`status` に `Args:` として出す。
- 手順の文面（`prompt`、`notes`、選択肢の `when`）の `{{arg.<名前>}}` を、`render_step` が run の値で置き換える。`run` の argv には展開しない（コマンドへ任意の文字列が入るのを避ける）。`dry-run` は置き換えず、書かれたまま出す。
- lint は、ルート定義の文字列に書かれた未宣言の `{{arg.x}}` をエラー（`unknown-arg`）にする（`{ file = ... }` の中は検査しない。実行時にエラー）。引数名の形式違反は `arg-name`。部品（include される定義）に `[args]` は書けない（`include-args`）。部品の文面は、ルートの引数を参照できる。

### 6.1 include（定義の部品化、B-017）

共通の手順（テストの実行、レビュー依頼など）を別ファイルに切り出し、複数の定義から使う。読み込み時に 1 枚の状態機械へ展開するので、run の仕組み（状態ファイル、遷移、`max_visits`）は変わらない。

```toml
[states.test]
include = "parts/test.toml"
exits = { ok = "review", fail = "fix" }   # 部品の終了ステートID = このファイルのステートID
```

- **部品**は通常の定義と同じ書式（`schema` / `start` / `notes` / `states`）。部品の中でも include できる（入れ子）。
- **include ステート**に書けるキーは `include` と `exits` だけ。`prompt` や遷移は書かない（`include-with-other-keys`）。
- **展開後の ID** は `<include ステートID>__<部品のステートID>`（入れ子は `a__b__c`）。include ステートへの遷移は、部品の `start` への遷移になる。ID が衝突したら lint エラー（`id-collision`）。部品の `start` が終了ステートなら `include-start-end`。
- **終了ステート**: 部品の終了ステートは展開後に残らない。部品の中から終了ステート `E` への遷移（`goto` / `choices` / `on_exceed`）は、`exits` の `E` に書いたステートへの遷移に置き換わる。`exits` は部品の終了ステートをすべて網羅する（`exits-missing`）。部品にない終了ステートを書くとエラー（`exits-unknown`）。
- **`notes`**: 部品の `notes.always` は部品のステートにだけ、親の `always` は親のステートにだけ付く。部品の `notes.common` の名前は `<include ステートID>__<名前>` になる（部品のステートの `notes` も同じく直す）。
- **`max_visits` / `on_exceed`**: 部品の中で閉じる。訪問回数は展開後の ID で数える。`on_exceed` が終了ステートを指すときは `exits` を通る。
- **循環**: include の循環（自分自身を含む）は `include-cycle`。判定は、展開中の部品の祖先（解決後のパス）で行う。同じ部品を複数回（別の親や、ひし形）使うのは許す。再帰は書けない。
- **パス**:
  - `include` のパスは、書いた定義のあるディレクトリの内側に限る（`..` と絶対パスは `include-outside`）。この判定は書かれたパスの字句で行い、symlink は解決しない。symlink で部品を共有できるようにするための、`{ file = ... }`（解決してから判定する）との意図的な違い。
  - 部品の `{ file = ... }`、`cwd`、`run` の `${DEF_DIR}` は、部品のファイルがあるディレクトリが基準。展開時に、ルートの定義ディレクトリ基準に書き直す（`${DEF_DIR}` は `${DEF_DIR}/<部品の相対ディレクトリ>` になる）。
- **lint**: 部品のスキーマ違反は、部品のパスを付けて報告する。到達不能・行き止まり・ループの検査は、展開後の状態機械に対して行う。
- **定義のハッシュ**（`run.definition_hash`）: include がなければ従来どおりルートファイルの sha256。あれば、ルートとすべての部品（相対パスを含む）のハッシュ。部品を書き換えると、`next` は `definition changed` になる。
- **コマンドの実行**: ルートと部品の**すべて**が `--ref` のコピーと一致するときだけ実行する（symlink は、リンク先の実体を、それを含むリポジトリの `ref` と比べる）。一つでも違えば表示のみ。
- **`rename`**: `exits` の値（親のステートID）は書き換えない（B-037）。参照が切れる rename は lint エラーで拒否され、ファイルは変わらない。

## 7. 状態ファイル

- 場所: git のルート（リポジトリ外では作業ディレクトリ）の `.flow/runs/<run-id>.json`（`.gitignore` へ追加を推奨）。
- 内容: `schema`、定義ファイルのパスとハッシュ、現在のステート、各ステートの訪問回数、履歴（ステート・選んだラベル・時刻）、状態（`running` / `ended`）。
- run-id はエンジンが採番する（時刻 + 短い乱数）。複数の run を並行して持てる。

## 8. CLI

| コマンド | 動作 |
|---|---|
| `flow start <定義> [--arg key=value ...]` | run を作成し、最初のステップを出力する。`--arg` は §6.2 の引数（B-018）。 |
| `flow next <run-id> --result <label>` | 判定を記録して遷移し、次のステップを出力する。 |
| `flow status <run-id>` | 現在地・訪問回数・履歴を出力する。中断後の再開に使う。 |
| `flow lint <定義> [--format text\|json\|github]` | 構造を検査する。エラーがあれば終了コード 1。`json` は `{"file", "issues": [{level, code, where, message}]}`、`github` は `::error file=<定義>::...` / `::warning ...`（Issue は行番号を持たないので file のみ）。`json` / `github` では、TOML を読めない場合も `read-error` の issue として出力する（B-008）。 |
| `flow dry-run <定義> [--results a,b,c]` | 状態ファイルを作らずに、定義を辿った出力を確認する。`--results` を省くと、全ステートの出力を一覧する。 |
| `flow test <定義> <シナリオ>` | シナリオ TOML（`[[scenario]]` に `name`、`choices`＝判断の列、`expect`＝開始ステートから終了ステートまで通るステート ID の列）を、定義を実際に辿って検証する（B-015）。`max_visits` / `on_exceed` も本物の実行どおりに効くので、上限超過の経路も書ける。`run` のステートは実行しない。判断の過不足・不明なラベル・期待との不一致は `FAIL`。1 つでも失敗すれば終了コード 1。目視用の `dry-run` と違い自動検証用で、手順の文面は比べない（スナップショット比較はしない）。 |
| `flow graph <定義>` | 状態遷移を Mermaid の `flowchart TD` として出力する（B-007）。`goto` と `choices`（ラベル付き）は実線、`on_exceed` は破線（`max N`）。ノード ID は `n_<ID>` で、`end` などの予約語を避ける。実行履歴の重ね表示と DOT 出力はしない。 |
| `flow rename <定義> <旧ID> <新ID>` | ステート ID を、すべての参照も含めて改名する。実行後に lint を通し、失敗したら元に戻す。 |
| `flow new <定義>` | 固定の雛形（`do_work` → `check` → 修正ループ → 報告）を書き出す。既存のファイルは上書きせずエラーにする（B-021）。出力は `fmt` の出力と一致する。 |
| `flow fmt <定義> [--check]` | キーの順序（ステートは `prompt, notes, delegate, gate, run, …, goto, end, max_visits, on_exceed`、選択肢は `label, when, goto`）と書式（`key = value`、テーブル間は空行 1 つ）をそろえて上書きする。標準ライブラリだけの行単位の整形で、コメントは直下のキーと一緒に動き、末尾コメントのある行と複数行文字列はそのまま保つ。整形前後で TOML のデータが変わるときは書き込まずエラーにする。裸のキー以外（引用符付き・ドットキー）は未対応でエラー。`--check` は書き込まず、変わるなら終了コード 1。 |

### ステップの出力（LLM に渡す内容）

```
[s1_1] (run: 20261122-1530-a3f)
<prompt text>

Notes:
- Do not do xyz
- Watch out for abc

After finishing the work, report the result with one of the following:
  flow next 20261122-1530-a3f --result xxx   : The build succeeded with 0 warnings
  flow next 20261122-1530-a3f --result other : Anything else
```

- 次に実行するコマンドは、**完成形で**出力する。
- 分岐なしのステップは、`--result` なしの `flow next <run-id>` を案内する。
- 終了ステップは、本文を出力して run を `ended` にし、最後に `Flow complete.` と明示する。
- 出力の定型文（見出し、案内文）は**英語**に固定する。ツールを日本語話者以外も使えるようにするため。定義の本文は、書いた言語のまま出力する。
- 不正なラベルは、状態を変えずにエラーとし、選べるラベルを再掲する。

## 9. linter

**エラー**（終了コード 1）

- `schema` 欠落・未対応、`start` 欠落、未知のキー、`delegate` がエージェント名の形式でない、または終了ステートにある
- ID の形式違反、遷移先（`goto` / `on_exceed` / `start`）が存在しない
- `goto` / `choices` / `end` が 0 個、または 2 個以上
- `end` のステートに遷移（`goto` / `choices` / `max_visits` / `on_exceed`）がある
- `choices` の `label` 重複、`when` 欠落
- `max_visits` があるのに `on_exceed` がない
- `on_exceed` があるのに `max_visits` がない（`on_exceed` は上限を超えたときにだけ使われ、`max_visits` なしでは、行き先の判定が実行と食い違う）
- `prompt` 欠落
- `{ file }` のファイルが存在しない、または定義ディレクトリの外
- `notes` の参照先が `common` にない
- **孤児ステート**: `start` から到達できない
- **`on_exceed` だけの循環**（`on-exceed-cycle`）: `on_exceed` の遷移だけで輪になっている（上限を超えると実行時に抜けられなくなる）
- **行き止まり / 無限ループ**: `start` から到達できるステートのうち、`end` へ到達できないものがある（`max_visits` の `on_exceed` 経路を含めて判定する）

**警告**

- どのステートからも参照されない `common` の注意書き
- 選べる分岐が 1 つしかない `choices`
- `max_visits` を持つステートを含まない循環（抜けられるかが LLM の判定だけに依存する）

## 10. skill からの使い方

feature 側の `SKILL.md` は、次の固定ループだけを書く（本文は数行）。

- `flow start <同じディレクトリの flow.toml>` を実行する。
- 出力の指示に従って作業し、出力に書かれた `flow next …` を実行する。
- `Flow complete.` と出るまで繰り返す。

`allowed-tools` で、`flow.py` の実行コマンドだけを許可する。`${CLAUDE_PLUGIN_ROOT}` の展開と承認の省略は、初版の完了条件として実機で確認する（B-005）。

## 11. 成功の基準

- 3 つの問題が解消される。(1) 改名は `flow rename` 1 回で済む。(2) 行き先なし・孤児・無限ループは `flow lint` が検出する。(3) 実行中に LLM へ渡るのは現在のステップの情報だけである。
- 既存の手順書型 skill を 1 つ、定義へ移して動かし、同じ結果が得られる。

## 12. 実装者に任せる点（私の判断として決めておくもの）

- **`max_visits` の数え方**: 「入った回数が上限に達していたら、次の入場は `on_exceed` へ」とした。「最大 2 周」は `max_visits = 2`。
- **定義が実行中に変わった場合**: ハッシュが一致しないとき、`flow next` は拒否し、`--force` で続行できるようにする。
- **run-id の形式**、出力文の細かい言い回し、`--json` 出力の有無。
- **`flow rename` の実装方法**: 標準ライブラリに TOML の書き出しがないため、テキスト置換で行う。置換後の `flow lint` による検証を必須とする。
- **core プラグインの skill の分割**（作成支援とレビュー・デバッグ支援）と、その細部。
